# 招标发现、核验与统计流程

本文根据用户提供的《查找招标网音视频与RTC项目》对话整理；对话中最后一轮业务核验发生于 2026-11-12。这里保留可复用的工作方法，不导入原对话里的生产账号、企业材料、投标报价、私人联系方式或历史项目数据。对话中的公告与截止日期不能当作当前仍有效的机会。

## 1. 明确本次搜索范围

- 使用北京时间 `Asia/Shanghai` 记录本次运行时间、查询窗口和核验时间。
- 优先纯软件开发，其次软件授权/服务；重点关注音视频、RTC、实时通信、直播、语音引擎、智能客服、视频平台及其运维。
- 将包含硬件、原厂授权、驻场、严格业绩、企业规模或证书条件的项目单独标注，不把技术匹配直接当成投标资格满足。
- 公告发布时间、报名截止、领件截止、响应截止、开标时间、澄清期限分别记录；查询时间窗不代替截止日期核验。

`config/search-presets.json` 保存从对话整理的查询词组。`config/discovery-sources.json` 保存公开来源和人工入口；这些地址需要运行时访问核实，配置本身不证明站点可用。

## 2. 在线发现候选

1. 查询采购人官网、政府采购平台、电信及铁塔采购平台、高校采购平台；再用搜索引擎和第三方转载补充线索。
2. 每条候选保留标题、采购人、项目/标包编号、来源 URL、公告日期、采集时间和匹配关键词。
3. 逐来源保存成功/失败状态。HTTP 403、登录页、验证码、动态防护或解析失败都不是“没有项目”。保留失败原因和人工访问入口。
4. 第三方转载只能作为线索，入库前尽量回到采购人原文。标注 `待核实`，不要凭搜索摘要推断预算、日期或资格。
5. 以采购人 + 项目编号 + 标包去重；没有编号时结合标准化标题和原公告 URL。更正、延期、第二次采购应关联原项目并保留版本，不能只按相似标题删掉。
6. 搜索结果和后台项目台账分开保存；核验后再纳入台账，保留人工选择和参与决策。

历史限制：对话记录过中国政府采购网四个栏目返回 HTTP 403。这是历史观察，需要每轮重新检测；禁止通过关闭 TLS 验证或绕过登录、验证码来掩盖失败。

## 3. 核验资格、交付与成本

每个候选至少核对以下信息，并把来源与核验时间写入记录：

| 类别 | 记录内容 |
| --- | --- |
| 范围 | 纯软件/软硬件混合/软件授权/技术服务，功能、集成、数据迁移、源码及知识产权要求 |
| 金额 | 预算/最高限价/框架预估/单价，币种，含税/不含税/未明确，不混合求和 |
| 资格 | 企业规模、业绩金额及时间、合同证明、社保税务、原厂授权、联合体及代理商限制 |
| 交付 | 工期、部署位置、现场服务、质保、验收及付款节点 |
| 截止 | 报名、领件、响应、开标、澄清及保证金截止，是否有延期或更正 |
| 证书 | 平台认可的 CA 类型、申请入口、有效期、主体一致性、签章/加密用途 |
| 风险 | 文件互相矛盾、缺失附件、合同模板错误、资格不明、截止时刻不明 |

资格门槛、交付难度、保证金和评分加分项分别描述。未知值保留未知；不能把“未披露”写成零，把“没有写要求”写成“无要求”。

## 4. 领取和解析采购文件

1. 遍历未过期、未放弃的项目，先处理今日/近期截止和已申请但未收到文件的项目。
2. 公开可下载的文件保存原始 URL、下载时间、原文件名和 SHA-256；检验 HTTP 状态、内容类型与文件签名，防止把登录页保存为 PDF。
3. 检查公告、更正、采购正文、技术规范、合同及补充附件是否齐全；分别标记登记表、需求稿、公告、完整采购文件。
4. 解析正文后产出资格、功能、人员、工期、保证金、报价、评分、付款、CA、提交方式等要点；标注页码或章节及未解决问题。
5. **下载公开附件不等于完成正式领件。** 只有平台领件记录/回执或采购人书面确认充分时，才把领取状态改为“已领取”。
6. 无法直接领取时，逐项记录官方登录入口、菜单路径、查询项目编号、所需材料、费用、CA要求、截止时间和后续动作。已过领件期必须先取得补领确认，不能继续当作仍可报名。
7. 登录、验证码、付费、报名提交、邮件发送或现场办理按本次实际授权处理；自动化只记录待办，不能仅因历史对话曾做过就再次执行。
8. 公告仅写日期而无时刻时，保留 `date_only` 与“确切时刻未确认”；统计中按当日结束处理只是展示规则，不作为可以延期操作的依据。

## 5. 台账更新

- 原数据先导出/备份；更新采用版本号，冲突时重读，避免覆盖其他人的编辑。
- 保留用户的参与决定、阶段、负责人、CA办理状态、已有材料和附件。
- 每次新增或更新都写审计记录：时间、操作者、来源、修改内容和核验限制。
- 置顶只影响排序；弃标标记为“放弃”，从默认台账、已过期和日历隐藏，保留独立列表和恢复入口。
- 恢复时保留原截止时间、领件状态和附件，并重新计算当前/过期状态。
- 验证未登录请求不能读取项目、导出或附件；已上传文件下载后的哈希应与原文件一致。

## 6. 统计与报告

同一批报告使用相同的 `as_of` 北京时间，至少给出：

- 本轮抓取来源数、成功/失败来源、候选数、去重数、新增/更新数、待核实数；失败来源单独列出。
- 全部项目、当前项目、已过期、已弃标，以及未来 7 天有有效截止节点的项目数；一个项目多个节点只计为一个项目。
- 未领取/已申请/已领取/已截止，CA 待确认/待办理/办理中/已办理/即将到期。
- 预算按币种、税口径和预算性质分组；未披露项单独计数，不把预算当收入。
- 生成 JSON 作为机器可读结果，CSV/Markdown 供人审阅；包含数据来源、核验时间、统计定义及不完整来源。

当前状态规则源于对话中的实际代码片段与最后一轮功能说明。按以下顺序判断，先匹配的规则优先：

1. 已放弃进入独立弃标列表；成交、未成交、已结束进入历史归档。
2. 已递交的项目继续跟进结果，响应截止已过不等于结束。
3. 其他项目若有效响应截止已过，归为已过期；已申请或已领取不豁免响应截止。
4. 尚无过期响应节点，但领件截止已过时：已领取继续跟进；已申请继续保留，明确标注“待确认是否可领取”；未申请且未领取归为已过期。
5. 其余项目保留在当前列表；日期矛盾、未知或资格不明确时附上“待核实”，不能据此认定可以报名。

仅使用 `is_current != false` 的有效节点；澄清或开标节点不能代替响应截止来判定整个项目过期。明确时刻按北京时间比较；仅日期节点在次日零点后算过期，但必须提醒确切截止时刻未确认。正式延期保留旧节点及来源，启用新节点后重新归类。列表、统计和日历采用同一口径；恢复弃标项目也重新计算。

## 7. 执行结果与“最新”含义

只有本次实际在线抓取并记录时间的结果可以描述为“本轮最新查询”。对话里的 2026-11-12 数量、历史公告和历史验收结果只说明需求来源，不证明当前线上状态，也不作为默认种子数据。

建议每个运行目录保存：`run.json`（时间和参数）、`sources.json`（逐来源结果）、`candidates.json`（待核验候选）、`reviewed.json`（核验记录）、`summary.json` 和 `report.md`。运行产物、采购文件和生产数据保存在被 Git 忽略的本地目录，不随代码提交。

## 每日执行清单与查询模板

1. **开始运行**：记下北京时间 `as_of`，读取现有台账，导出受保护的备份；筛出未放弃的当前项目，按今日截止、未来 7 天、已申请待确认、其他项目排序。
2. **先查变更**：对现有项目以及本轮关注的近期过期项目，用精确项目编号搜索“更正／延期／变更／终止／第二次”，返回正式采购平台核对，先修正截止时间再判断是否过期。这样可发现延期后重新开放的机会。新公告替代旧节点时将旧节点 `is_current` 设为 false，保留原记录与来源；再次采购则关联原项目，同时区分新一轮采购与原标包。
3. **发现新项目**：按以下模板逐词组检索。`{window_start}`、`{window_end}` 使用本轮日期，`{keyword}` 从配置逐项取值，`{domain}` 使用官方来源域名；不要把所有关键词拼成必须同时匹配的一个条件。

   ```text
   "{keyword}" "采购公告" after:{window_start} before:{window_end}
   "{keyword}" "招标公告" after:{window_start} before:{window_end}
   "{keyword}" "软件开发服务" after:{window_start} before:{window_end}
   site:{domain} "{keyword}" "询比"
   "{project_code}" "更正"
   "{project_code}" "延期"
   "{project_title}" "第二次"
   ```

   若需包含今天的公告，`window_end` 使用北京时间次日日期，因为 `before` 通常不含指定日期。搜索引擎的 `after`/`before` 是候选筛选提示，可能按索引时间匹配。必须打开公告核对实际发布日期，不能据此证明属于时间窗；截止日期也必须独立核对。搜索未命中时记录查询条件，而不是认定没有机会。配置中的 `review_dimensions` 仅用于人工资格核对，不能作为搜索排除词。

4. **逐条核验**：打开候选原文、采购附件和变更记录，按本文第 3 节补齐字段；找不到原文或有冲突时保留待核实及下一步。
5. **领件检查**：按第 4 节下载允许直接访问的文件并解析；平台登录、付费、邮件、现场等步骤生成项目专属指引。停止在需要用户操作的位置，保留未完成的真实状态。
6. **入库与复核**：执行版本检查、去重和更新，检查附件可下载、操作记录齐全；抽查标题、编号、预算、三个主要截止点和 CA 是否对应同一标包。
7. **产出统计**：按下表统计，并列出本轮失败来源、待核实项目及今日需人工处理事项；完成后记录 `finished_at` 和总耗时。

| 指标 | 口径 |
| --- | --- |
| 抓取来源成功数 | 本轮请求完成且解析到有效页面的来源；收到 200 登录页不算成功 |
| 候选数 | 原始候选数量；同时报告标准化去重后的数量 |
| 新增数／更新数 | 相比运行前台账的项目数量；仅修改多个字段仍计一个更新项目 |
| 当前项目 | 非放弃、非终态，且没有按有效节点判定过期的项目；已申请待回执与已递交待结果需单列 |
| 未来 7 天截止 | 当前项目中至少一个有效节点在 `[as_of, as_of + 7 天]` 内的项目；按项目去重，同时提供节点清单 |
| 待领取 | 当前项目中未取得完整文件的项目；“已申请待确认”单列，不能算已领取 |
| CA 待落实 | 当前项目关联证书未确认、未办理、办理中或已失效；要求不明单列，不能写成不需要 CA |
| 未披露预算 | 未公开金额的项目个数；不参与任何金额加总 |

建议保存的人工核验记录模板：

```json
{
  "project_id": "project-or-lot-stable-id",
  "checked_at": "填写带 +08:00 的 ISO 8601 时间",
  "official_notice_url": "填写正式公告 URL",
  "amendment_urls": [],
  "verification_status": "待核实",
  "documents_complete": false,
  "formal_receipt_confirmed": false,
  "receipt_evidence": "平台回执或采购人确认；没有则留空",
  "manual_steps": [],
  "limitations": [],
  "next_action": "下一步动作和负责人"
}
```

该模板描述核验产物，不宣称是尚未迁入仓库的原后台 API 格式。将来对接时应以原后台真实字段和版本控制接口为准。
